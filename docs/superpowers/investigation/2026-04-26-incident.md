## Hypothesis verification

### Bug #4 (CG audible after global restore)

**CONFIRMED sub-cause: CG track-level mute is not captured in `track_mutes`.**

The backup files DO capture CG correctly in the `sends` array (all 10 sends `mute: True`). The send-level restore correctly unmutes/mutes CG sends if they differ from backup. However:

1. `backup_capture.rs` line 171 filters `track_mutes` to tracks whose name contains "inear" or "stems". CG matches neither, so its **track-level mute** is never saved.
2. If the CG track itself is track-muted in REAPER at backup time (possible operational usage), that state is never restored. Only the 10 send-level mutes are restored.
3. Additionally, the "skip-if-unchanged" optimization means that if CG sends were already muted at restore time (matching backup), they are silently skipped — no write occurs. This is correct behavior, but means if CG's track mute was removed externally (e.g., REAPER project reload cleared it), the restore won't catch it since CG track mute is not in `track_mutes`.

The primary fix needed: add CG (and any other non-inear/non-stems source tracks that have mute state worth preserving) to the `track_mutes` capture filter. OR make the filter include all tracks (or all non-input tracks).

The hypothesis "backup predates CG" is **FALSIFIED** — CG was added 2026-04-20 23:47, and ALL backups used for the April 21 restores (07:04, 13:00) are dated AFTER CG was added.

The hypothesis "partial capture" is **PARTIALLY CONFIRMED** — sends are captured correctly (259 sends, 10 CG sends present), but `track_mutes` does not include CG.

### Bug #3 (Petronela faders unexpected after 21.4 restore)

**INCONCLUSIVE — file looks structurally fine.** The 21.4 backup contains Petronela's sends with plausible values (26 sends to PETRONELA inear; `PETRONELA mic → PETRONELA inear vol=1.0, STEVO mic → PETRONELA inear vol=0.708`). The track volume for `PETRONELA inear = 0.131826` (≈ −17.6 dB linear) is very low. This is the *master fader* for Petronela's bus. If Petronela's fader "felt wrong" after restore, it is likely because:

- The master fader was stored in the backup at −17.6 dB and correctly restored to −17.6 dB, but that low value was not the expected starting point for April 21 soundcheck.
- Alternatively, if Petronela had adjusted her mix between the backup timestamp and the restore, the restore correctly rolled those changes back.

No evidence of file truncation or missing Petronela data. The backup file appears complete.

### Bug #1 (Tina's 19.4 missing from her snapshot history)

**CONFIRMED cause: auto-snapshot did not fire on 2026-04-19 because Tina's WebSocket never connected.**

- The snapshot file is a single JSON array (not per-day directory). The April 19 entry is definitively absent.
- The daemon log for April 19 confirms auto-snapshots ran for 9 other members (engineer, petronela, stevo, zuzka, mirec, alex, marek, patrika, ani) but NOT tina.
- The poller *discovered* Tina's track from REAPER on April 19 (track routing was there), but no `WebSocket connected member_id=tina` entry appears in the April 19 log.
- **Conclusion:** Tina did not connect her device on April 19. The snapshot trigger is connection-based. This is expected behavior — the system is working as designed. The 14-day gap (April 8–23) suggests Tina simply did not use the app during that period.
- **No UI bug.** The list accurately shows what snapshots exist. The missing entry is not a display bug.

### Bug #2 (Stevo cross-contamination during Tina restore)

**NO ON-DISK EVIDENCE** — as expected. The restore code in `apply_restore` processes sends by name lookup (`track_map.get(&send.src_name)` and `track_map.get(&send.dest_name)`), which could in theory map to wrong tracks if names changed in REAPER between backup and restore. However, no evidence of name changes in the track layout exists in the logs. This bug requires a T9 reproducer test to probe whether restoring one member's snapshot erroneously writes to another member's state.
